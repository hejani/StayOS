### 2.1 LUMI backend failures (2, both real)

**F-1 — `test_get_brief_404_when_no_brief_exists`**
`lumi/backend/tests/unit/test_briefs_handler.py`

The `propertyId` validator in `briefs_handler._validate_property_ownership` was
tightened to `^ALOHA-[A-Z]{3}-\d{3}$`. The test's fixture `propertyId` no longer
matches, so the handler returns `400` before reaching the `404` path the test
asserts. **Fix:** update the test fixture to a conforming ID.

**F-2 — `test_invalid_float_value`**
`lumi/backend/tests/unit/test_settings_validator.py:181`

`lumi/backend/functions/api/validators/settings_validator.py:82` coerces the
occupancy threshold with `int(occ_val)` and its docstring states it "accepts int,
float, Decimal, or numeric string". The test asserts float `70.5` must be
rejected. Code and test now disagree. **Fix:** decide the contract — either
reject non-integral values explicitly or delete the test's float case.

### 2.2 Import-time environment dependency

`lumi/backend/functions/seed-data/seed_data.py:28` reads
`os.environ["DEMO_PASSWORD"]` **at module import**:

```python
DEMO_PASSWORD = os.environ["DEMO_PASSWORD"]
```

`lumi/backend/tests/conftest.py:78` does set `DEMO_PASSWORD` via `monkeypatch`,
but `monkeypatch` is a per-test fixture that runs *after* pytest's collection
phase imports the module — so the whole LUMI backend suite fails collection with
`KeyError: 'DEMO_PASSWORD'` unless the variable is exported in the shell first:

```bash
DEMO_PASSWORD='TestOnly!Pass123' python3 -m pytest -q
```

(A weak value also fails: Cognito rejects it with `InvalidPasswordException`
against the pool's password policy.)

This works in the deployed Lambda because CloudFormation sets the variable, but
it blocks local test runs, cold-start diagnostics, and any reuse of the module.
**Fix:** read the variable lazily inside the one function that needs it, or
default to `None` at module scope and fail loudly at the call site.

### P1 — correctness / operational risk

> **All four P1 findings below (CR-1…CR-4) were fixed on 2026-09-01.** Each is

#### CR-1 · PULSE can be left silently suppressed
`pulse/backend/src/pulse/rule_engine/quiesce.py:153`

`LambdaEsmGateway.set_enabled` catches only `ResourceNotFoundException`.
`ResourceConflictException` (raised when the event source mapping is still
`Enabling`/`Disabling` — the common race), `TooManyRequestsException`, and
`ServiceException` all escape: `_toggle_all` catches only `QuiesceError`, so they
propagate past `unquiesce_rule_engine`'s bounded-retry and CRITICAL-log path.

**Failure scenario:** the state machine takes its `Catch` route; un-quiesce is
throttled or hits a still-transitioning ESM; the handler raises with one or more
ESMs still disabled. PULSE stops evaluating streams with no alarm — the exact
outcome Requirement 5.5 and the `docs/data-model.md` claim ("its `Catch` path
always un-quiesces so PULSE is never left suppressed") forbid.

**Fix:** catch the full set of retryable Lambda exceptions in `set_enabled` and
map them into `QuiesceError` so the existing retry + CRITICAL-log path engages.

> **Status: FIXED (2026-09-01).** `LambdaEsmGateway.set_enabled` now catches
> `ResourceNotFoundException`, `ResourceConflictException`,
> `TooManyRequestsException`, and `ServiceException` and maps all of them to
> `QuiesceError`, so `_toggle_all` records the UUID as failed and the
> bounded-retry + CRITICAL-log path in `unquiesce_rule_engine` engages instead
> of the exception escaping. Covered by new gateway-level tests in
> `pulse/backend/tests/rule_engine/test_quiesce.py`
> (`test_gateway_maps_retryable_lambda_errors_to_quiesce_error`,
> `test_gateway_conflict_during_unquiesce_engages_retry_and_critical_log`).
> PULSE backend suite: 291 passed, 3 skipped.

#### CR-2 · Rooms table is not idempotent under the real Generate → Reconcile flow
`lumi/backend/functions/seed-data/dataset_generator/rooms_generator.py:312`

`reconcile_room_status` writes only rooms that *currently* have an active
reservation or work order. Rooms whose prior `OCCUPIED` / `OOO` / `MAINTENANCE`
state has gone stale are never reset to `AVAILABLE`.

This appears to work today only because `generate_rooms` runs first with
`idempotent=True`, and its baseline row (`status=AVAILABLE`, no `currentGuestId`)
differs from the previously-reconciled row — so the writer rewrites **all ~1,250
rooms every single day**.

**Failure scenario:** the idempotency guarantee asserted in
`generation_runner.run_generation` (Property 2 / Requirement 2.4) does not hold
for `stayos-rooms`. `TestRollForwardIsIdempotent` only exercises
Generate → Generate with no Reconcile between, so the regression is invisible to
the suite.

**Fix:** make `reconcile_room_status` emit an explicit reset-to-`AVAILABLE` for
rooms with no active reservation/work order, and extend the property test to
cover Generate → Reconcile → Generate.

> **Status: FIXED (2026-09-01).** `reconcile_room_status` now iterates every
> known room in `rooms_lookup` and explicitly resets any room with no active
> reservation/work order to `AVAILABLE` (null guest and work order), so the
> reconciled state depends only on the current reference date rather than
> whatever the table held before. A new `available` counter is reported in the
> returned counts (and threaded through `reconciledCounts`). Covered by
> `test_stale_status_reset_to_available_on_reconcile` (the Reconcile → Reconcile
> stale-status scenario) in `lumi/backend/tests/unit/test_rooms_generator.py`;
> the existing reconcile tests and the shared integration test
> (`test_reconcile_returns_counts_and_updates_rooms`) were updated to the new
> counts contract. LUMI rooms suite: 41 passed; shared/data-orchestrator: 63
> passed.

#### CR-3 · Unpaginated `Scan` silently loses the settings row
`shared/data-orchestrator/handlers/regenerate_brief_handler.py:316`

```python
table.scan(FilterExpression="propertyId = :pid", ...)
```
… then returns `items[0]`. DynamoDB applies `FilterExpression` *after* reading a
1 MB page, so as `stayos-settings` grows the matching item can land past page 1.

**Failure scenario:** the property silently becomes "no GM settings found";
every roll-forward records `status=FAILED, reason=no-gm-alias` with nothing
indicating the real cause is scan pagination.

**Fix:** use `Query` on the `gmAlias` key or paginate the scan.

> **Status: FIXED (2026-09-01).** `_read_property_schedule` now paginates the
> scan via `LastEvaluatedKey`, collecting matches across all pages instead of
> reading only page 1's `items[0]`. (A `Query` is not available: the settings
> table's partition key is `gmAlias` and the data model defines no `propertyId`
> GSI.) On multiple matches it sorts by `gmAlias`, takes the lowest
> deterministically, and logs a warning rather than depending on page ordering.
> Covered by `test_read_property_schedule_finds_match_on_later_page` and
> `test_read_property_schedule_none_when_no_page_matches` in
> `shared/data-orchestrator/tests/test_ordering_guard.py`.

#### CR-4 · One malformed settings row aborts every remaining property
`shared/data-orchestrator/handlers/regenerate_brief_handler.py:202`

`_delivery_datetime_on` does `hour_str, minute_str = delivery_time.split(":")`
followed by `int(...)`. Any malformed `briefDeliveryTime` (missing colon,
non-numeric, `"24:00"`) raises `ValueError`. That call sits in the
`for property_id in targets:` loop of `regenerate_briefs` but **outside** the
per-property `try/except BriefRegenerationError`.

**Failure scenario:** a single bad settings row aborts brief regeneration for all
subsequent properties and raises out of the step.

**Fix:** move the guard call inside the per-property `try`, or validate and
`raise BriefRegenerationError` so the existing per-property handling applies.

> **Status: FIXED (2026-09-01).** `_delivery_datetime_on` now raises a clear
> `ValueError` on any malformed `HH:MM` (wrong shape, non-numeric, or
> out-of-range like `"24:00"` — the latter rejected by `datetime.time`). The
> `check_ordering_guard` call was moved inside the per-property `try` in
> `regenerate_briefs`, and its `ValueError` is converted to a per-property
> `BriefRegenerationError`, so one malformed `briefDeliveryTime` fails only its
> own property and the remaining properties still regenerate. Covered by
> `test_malformed_delivery_time_isolated_to_its_property` in
> `shared/data-orchestrator/tests/test_ordering_guard.py`.

### P2 — efficiency / robustness

#### CR-5 · `run_reconcile` reruns the entire generation pipeline
`shared/data-orchestrator/handlers/generation_runner.py:301`

`run_reconcile` calls `run_generation(...)` purely to rebuild the in-memory
`reservations` / `work_orders` / `rooms_lookup` structures. That reruns the full
deterministic pipeline including the `BatchGetItem` read-back in
`_filter_changed_items` across ~50k items — measurable extra latency and
DynamoDB read cost on every daily execution.

**Fix:** have `run_generation` return the built structures, or factor the pure
build step out from the write step.

#### CR-6 · Read-back failure silently downgrades idempotent to full write
`lumi/backend/functions/seed-data/dataset_generator/writer.py:263`

On any `ClientError` inside `_batch_get_existing`'s `BatchGetItem`, the code
`break`s and returns only what was collected so far. Every not-yet-fetched key is
then treated as "not stored" and rewritten.

**Failure scenario:** a transient throttle silently converts `idempotent=True`
into a full table rewrite. No counter or log distinguishes "wrote because the
item changed" from "wrote because the read-back failed".

**Fix:** retry the failed batch, and emit a distinct WARNING plus a counter when
falling back.

#### CR-7 · Execution-name truncation can drop the date suffix
`shared/data-orchestrator/handlers/concurrency_guard.py:127`

`build_execution_name` truncates `f"{prefix}-{propertyId}-{referenceDate}"` at 80
characters. A sanitized `propertyId` longer than ~65 chars slices off the
trailing `YYYY-MM-DD`.

**Failure scenario:** distinct dates collapse to one execution name, so every
subsequent day is skipped as `ExecutionAlreadyExists`. Nothing warns when the
truncation actually removes the date.

**Fix:** hash the property portion instead of truncating, or assert the date
suffix survives and warn otherwise.

#### CR-8 · Ordering-guard warning fires on the wrong scenario
`shared/data-orchestrator/handlers/regenerate_brief_handler.py:256`

`is_ordering_guard_satisfied` returns `completion_local < todays_cron`. When
roll-forward completes late in the local day — after the cron has already fired —
it reports a breach even though tomorrow's cron will run on fresh data.

**Failure scenario:** any completion after `delivery_time` logs a misleading
breach warning, degrading the observability signal it exists to provide.

**Fix:** compare against the *next* cron occurrence rather than today's.

> **Status: REJECTED as a false positive (2026-09-01) — no code change.** The
> proposed fix is incorrect: `next_brief_cron_fire()` returns the first cron
> fire *at or after* completion by construction, so
> `completion_local < next_brief_cron_fire(...)` is true in every case except an
> exact-second tie — comparing against the next occurrence would make the guard
> *never* breach, removing the exact signal it exists to provide, and would
> break the two breach tests (`test_check_ordering_guard_warns_on_breach`,
> `test_guard_uses_property_local_timezone`). The current
> `completion_local < todays_cron` is correct: it flags the real problem — this
> morning's brief already fired on stale (pre-roll-forward) data because the
> roll-forward finished too late — which all four existing ordering-guard tests
> assert. The only legitimate part of the finding is that the word "breach" in
> the log reads as more alarming than the self-healing (tomorrow's cron runs on
> the refreshed window) reality; that wording nuance was judged not worth a
> behavior change. Logic and tests left as-is.

## 6. Performance test harness

`perf/load_test.py` — asyncio + aiohttp + boto3 driver, added because no
environment existed to measure.

What it does:

1. Resolves the shared Cognito pool and the LUMI/PULSE API endpoints from the
   CloudFormation stack outputs of `stayos-us-east-1` and `pulse-us-east-1`.
2. Signs a seeded GM in via `ADMIN_USER_PASSWORD_AUTH`.
3. Fans out N virtual users, each running a weighted mix that mirrors a GM on
   the mobile PWA:

   | Scenario | Weight | Endpoint |
   |---|---|---|
   | `list_alerts` | 45% | `GET /alerts?tier=CRITICAL&status=UNACKNOWLEDGED` |
   | `get_vips` | 20% | `GET /vips` |
   | `get_brief` | 15% | `GET /briefs/{propertyId}` |
   | `get_ops` | 10% | `GET /ops` |
   | `fire_demo_scenario` | 5% | `POST /demo/scenarios/walk-risk` |
   | `acknowledge_alert` | 5% | `POST /alerts/{id}/acknowledgements` |

4. Reports p50 / p95 / p99 / max latency, error rate, and RPS per scenario.
5. Fails the run if the median of the read-path p95s exceeds **1500 ms**.

Run it after the next deploy:

```bash
GM_PASSWORD='<the APP_PASSWORD used at deploy-all>' \
python3 perf/load_test.py --duration 60 --concurrency 20
```

**Out of scope for this harness:** the two PULSE wall-clock SLOs (Req 1.1
rule-eval start ≤ 5s; Req 13.1/13.2 CRITICAL ≤ 30s / WARNING ≤ 120s). Those need
instrumented telemetry on the Streams → rule engine → AppSync path, and the
skipped closed-loop integration test is the right owner. This harness measures
the REST surface only.
