1. Two-layer architecture

LUMI layer — 7 stayos-* tables

5 read-only dataset tables (seeded once, ~24,000 items, 30 days of deterministic data across 5 properties, all streaming NEW_AND_OLD_IMAGES) plus 2 application tables.

stream on read-only read/write

PULSE layer — 5 pulse-* tables

PULSE owns these and never writes to LUMI tables — except the GM-approved closed-loop write-back via the Action Executor. Its rule engine consumes the 5 dataset streams to produce alerts.

Isolation boundary: everything partitioned by propertyId except stayos-settings & pulse-push-subscriptions (gmAlias), and pulse-alerts / pulse-alert-history (alertId).

pulse-action-executor is the only runtime writer into the LUMI operational tables, and only after GM approval. Its write-back re-enters the same stream, which resolves the originating alert.

All read paths scope every query/GetItem to a single propertyId (the DynamoDB partition key — the real data-isolation boundary, not an app-level filter). PULSE property scoping is additionally enforced server-side from the caller's Cognito claims.

8. Data volume — LUMI seeded (~24,756 items)

PULSE tables are runtime/demo-driven — on deploy they hold only seeded pulse-rules (30) and pulse-kitchen snapshots (5). Alerts, history, and subscriptions grow at runtime.
